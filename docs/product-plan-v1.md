# AI 五分钟 · 产品方案 v1

> 本版只讲产品和内容。视觉风格先不定，等内容形态验证后再单独设计。

> **一句话定位：每天早上 7:30，花 5 分钟读完 AI 圈过去 24 小时最重要的 12 件事。**
>
> Slogan 备选：「AI 圈大事，5 分钟说清」

---

## 0. 先说结论

| 问题 | 答案 |
| --- | --- |
| 我们是什么 | **AI 每日简报**，不是"AI 资讯聚合站"。每天一期，**读完就结束**。 |
| 卖点是什么 | **帮你挑过 + 用大白话说 + 每条有出处**。拼的是质量，不拼数量、不拼速度。 |
| 主攻谁 | 怕跟不上 AI 变化的**科技从业者**（产品、工程、运营、创业者）。他们天天来、也爱转发。 |
| MVP 做什么 | 4 个页面：今日、往期、单条分享落地页、后台。**不做登录，不做评论，不做无限刷新的信息流**。 |
| 内容怎么来 | **Manyfold Agent 起草，编辑花 10–15 分钟审核**，每天 7:30 准时发布。 |
| 靠什么留住人 | 天天不断更、质量稳定 + 一看就信得过 + 适合转发的分享卡片。 |

## 1. 用户画像

默认受众：**说中文的 AI 关注者**（中国大陆 + 海外华人）。如果只做其中一边，见第 12 节。

### A｜「怕跟不上的科技人」：核心用户 ★

- **典型的人**：小林，28 岁，互联网公司的产品经理 / 工程师，坐地铁通勤 40 分钟
- **什么时候看**：早上通勤刷手机，午休时再看一眼
- **想要什么**：知道今天 AI 圈出了什么事，开会、和同事聊天时不掉队；也想知道哪些事跟自己的工作有关
- **现在的痛点**：公众号标题党，同一条新闻十个号重复发；X 和英文一手信息来不及看；消息很多，却没人告诉他哪条重要
- **对我们的价值**：**打开频率最高、最爱转发**，是种子用户

### B｜「找机会的决策者」

- **典型的人**：陈总，38 岁，创业者 / 投资人
- **想要什么**：融资、公司战略、商业格局的变化，以及"这件事对行业意味着什么"
- **现在的痛点**：时间非常少，只信可靠的消息来源
- **对我们的价值**：人少但价值高，是以后付费 / 商业化的对象

### C｜「爱尝鲜的 AI 玩家」

- **典型的人**：阿杰，22 岁，学生 / 内容创作者 / 独立开发者
- **想要什么**：新工具、新模型能不能马上用上；能拿去发朋友圈 / 小红书的素材
- **现在的痛点**：好东西总是发现得太晚
- **对我们的价值**：**帮我们扩散内容**

### D｜「不想被时代落下的职场人」

- **典型的人**：王姐，35 岁，做市场 / HR / 教师
- **想要什么**：用大白话把事情讲清楚，看不懂的名词有解释
- **对我们的价值**：人数最多，是第二阶段扩大受众的目标

**结论**：MVP 主攻 A，兼顾 C。写作时照顾 D（给术语加解释），因为"说人话"对 A 同样是加分项。

## 2. 从需求到产品原则

| 用户原话 | 背后的需求 | 我们怎么做 |
| --- | --- | --- |
| "太多了，看不完" | 帮我筛 | 每天固定 ≤12 条，而且**有读完的终点** |
| "看了标题，不知道重不重要" | 帮我判断 | 每条都写一句"**为什么重要**" |
| "这消息靠谱吗？" | 可信 | 每条标一手来源和时间；传闻明确标出来；**更正记录公开** |
| "想转给同事 / 发朋友圈" | 社交谈资 | 一键生成好看的分享图 |
| "老是忘了看" | 需要提醒 | 固定时间发布；可以添加到手机主屏幕；P1 加邮件和推送提醒 |
| "专业名词看不懂" | 降低门槛 | 术语第一次出现时用括号解释 |

### 五条产品原则（做取舍时以此为准）

1. **有终点**：一期读完就结束。"读完了"是我们要给用户的感觉，这是功能，不是缺陷。
2. **30 秒也有收获**：打开第一屏就是"今日三件事"，只看这一眼也值。
3. **说人话，带数字**：标题 = 谁 + 做了什么 + 关键数字。
4. **每条能查到出处**：没有一手来源的不发。
5. **快**：打开 1 秒内能开始读，网络差也能用。

## 3. 内容设计（产品的核心）

### 3.1 把"5 分钟"拆成具体预算

中文阅读速度大约 350 字/分钟。所以 5 分钟不是口号，而是**硬性的字数上限**。

| 板块 | 内容 | 字数 | 阅读时间 |
| --- | --- | --- | --- |
| 今日三件事 | 3 句话，每句 ≤25 字，点一下跳到对应新闻 | ~75 | 15 秒 |
| 头条 | 1 条稍深入的：发生了什么 / 为什么重要 / 接下来关注什么 | ~350 | 60 秒 |
| 要闻 | 5–6 张标准新闻卡片 | 6 × 130 | 150 秒 |
| 快讯 | 5 条，每条一句话 | 5 × 35 | 35 秒 |
| 今日数字 + 值得一试 | 1 个抓眼球的数字 + 1 个新工具 | ~120 | 25 秒 |
| **合计** | **约 12 条** | **≤1,600 字** | **约 4.5 分钟** |

> 硬规则：**一期总字数不超过 1,600 字**。超了就删，不压缩字号。

### 3.2 一条新闻长什么样

| 字段 | 规则 |
| --- | --- |
| 分类 | 模型 · 产品 · 公司 · 融资 · 研究 · 开源 · 政策 · 硬件（最多 8 类） |
| 标题 | ≤22 字，谁 + 做了什么 + 关键数字 |
| 一句话摘要 | ≤60 字，说清发生了什么 |
| 为什么重要 | ≤45 字，说清对行业 / 读者的影响 |
| 关键数字 | 可选，在卡片上放大显示 |
| 来源 | 来源标签 + 来源名 + 原文链接 + 发布时间（必填，至少 1 个一手来源；展示方式见 3.10） |
| 展开详情 | 可选，3 个要点，点开才看到 |

示例（**格式演示，不是真实新闻**）：

```
[开源]
某实验室开源 70B 模型，推理成本降到同级闭源的 1/8
模型权重和训练报告同时公开，数学和代码评测接近一线闭源模型。
为什么重要：开源模型又一次逼近闭源上限，企业自己部署的成本门槛继续下降。
来源：官方博客 · 10/07 22:10  ↗
```

### 3.3 写作规范（也直接写进 Agent 的提示词）

- **标题公式**：谁 + 做了什么 + 关键数字或影响
  - ✅ 「XX 发布 YY，API 价格降 80%」
  - ❌ 「重磅！AI 圈今夜无眠」　❌ 「XX 要变天了？」
- **禁用词**：震惊、炸裂、重磅、颠覆、遥遥领先、王炸、杀疯了
- **数字要具体**：不写"大幅提升"，写"提升 37%"
- **术语第一次出现时加解释**：「MoE（混合专家：每次只调用部分参数，省算力）」
- **传闻要标出来**：加上 `传闻` 标签，未经证实的消息不上头条
- **国内外都要有**：每期至少 30% 是国内动态
- **拿不准的宁可不发**

### 3.4 怎么选题

每条候选新闻按 4 项打分（每项 1–5 分）：**影响多大 × 有多新 × 有多可信 × 读者有多关心**。

来源分三档：

- **T1**：官方公告、论文、财报、产品更新日志。可以上头条。
- **T2**：一线媒体，如 The Verge、TechCrunch、Bloomberg、The Information、36氪、机器之心、量子位。可以进要闻。
- **T3**：社交媒体、爆料。**只能进快讯，而且必须标"传闻"**。

### 3.5 发布节奏

- **每天 07:30（北京时间）发布**。利用时差：美国公司白天的发布正好落在北京凌晨，早上这一期刚好全部覆盖。
- **收录时间段**：前一天 06:00 到当天 06:00。
- **周一到周五出日报；周六出"一周回顾"**（本周 5 件大事，从本周已发内容自动汇总）；**周日休刊**。
- 连续阅读**按期数算，不按天数算**，所以休刊不会让用户的连续记录断掉。
- 遇到重大突发：不连发推送打扰用户，放到第二天头条。以后可以加"快报"。

### 3.6 内容生产流程

```
05:30  定时任务启动
  ↓    抓取信源：官方博客 RSS、HN、GitHub Trending、Hugging Face、arXiv、中英文科技媒体
  ↓    去重，把讲同一件事的报道归成一组
  ↓    抓取每个来源的原文快照，存进这条新闻的"资料包"（为 AI 追问做准备，见第 6 节）
  ↓    Manyfold Agent 打分、选题、按规范写稿（输出结构化 JSON）
  ↓    （P1 起）为每条生成 2–3 个预设追问，自动校验引用
  ↓    存为草稿
06:30  编辑在后台审核（10–15 分钟：删条目、改措辞、调顺序、核对来源链接）
07:30  定时发布 → 自动生成分享海报和社媒卡片
```

**原则：AI 起草，人做判断。** 如果 Agent 当天出不了稿，后台会提示，编辑可以手动补上。

### 3.7 首批信源清单

宁可少而准。上线时每个源都标好档位（T1/T2/T3），之后按实际出稿率增减。

| 类型 | 信源 | 档位 |
| --- | --- | --- |
| 海外模型公司 | OpenAI、Anthropic、Google DeepMind、Meta AI、Mistral、xAI 的官方博客 / 更新日志 | T1 |
| 国内模型公司 | DeepSeek、通义千问、Kimi（月之暗面）、智谱、MiniMax、字节豆包 / Seed、腾讯混元、百度文心的官方公告 / 公众号 | T1 |
| 平台和基础设施 | NVIDIA、Microsoft、AWS、Apple 的 AI 相关公告 | T1 |
| 开源和研究 | Hugging Face Trending、GitHub Trending、arXiv（cs.CL / cs.LG 高关注论文）、Papers with Code | T1 |
| 海外媒体 | The Verge、TechCrunch、Bloomberg Tech、Reuters Tech、The Information | T2 |
| 国内媒体 | 机器之心、量子位、36氪、晚点 LatePost | T2 |
| 社区信号 | Hacker News 首页、X 上的核心人物、即刻 AI 圈 | T3（只用来发现线索，写稿时要找到 T1/T2 来源） |

### 3.8 编辑审核清单（每天发布前过一遍）

10–15 分钟内过完，任何一项不过就改或删：

1. **来源**：每条的链接能打开吗？是一手来源吗？发布时间在收录窗口内吗？
2. **事实**：公司名、产品名、数字、日期和原文一致吗？（Agent 最容易出错的就是数字）
3. **标题**：符合"谁 + 做了什么 + 数字"吗？有没有禁用词、问号标题？
4. **为什么重要**：是真实判断，还是"这标志着 AI 进入新阶段"这类空话？空话就重写或删掉
5. **传闻**：未经官方证实的，标了 `传闻` 吗？有没有误上头条？
6. **重复**：和昨天那期重复吗？同一件事有没有拆成两条？
7. **配比**：国内动态至少 30% 了吗？总字数 ≤1,600 吗？
8. **今日三件事**：只看这 3 句，能不能大致知道今天发生了什么？
9. **预设追问**（P1 起）：头条的追问逐条看；其他条目抽查；程序校验没通过的必须看

### 3.9 内容质量闭环

- **每条新闻的数据**：展开率、原文点击率、分享次数，每周看一次，判断哪类选题读者真正在乎
- **读完页的轻反馈**：「今天这期 👍 有用 / 👎 一般」，一点就完成，不让写字
- **更正机制**：发现错误时，在原条目上标"已更正 + 更正说明"，同时记到 /about 的更正记录里。**不悄悄改**
- **每周复盘**：把 👎 最多的一期、展开率最低的 3 条拿出来，看是选题、写法还是篇幅的问题，再改进写作规范和 Agent 提示词

### 3.10 来源怎么展示（让读者一眼就信）

"有来源"只是底线。读者真正在意的是**这条消息从谁那儿来、到底确定不确定**。所以来源要分层展示：

**① 收起状态：一行"来源标签"，不点开也能判断可信度**

| 标签 | 什么时候用 | 卡片上的样子 |
| --- | --- | --- |
| `官方` | 公司公告、官方博客、论文、财报 | 官方 · OpenAI 博客 · 3 小时前 |
| `媒体` | 一线媒体的报道 | 据 The Information 报道 · 5 小时前 |
| `多方` | 2 家及以上独立来源报道了同一件事 | 官方 + 3 家媒体 · 2 小时前 |
| `传闻` | 爆料、未经官方证实 | 传闻 · 据 X 用户爆料，未证实 |

措辞上要区分"**××宣布**"（官方确认）和"**据××报道**"（媒体说法），让文字本身就带上可信度。

**② 展开状态：完整的来源列表**

- 每个来源都写：来源名、标签、发布时间、原文链接
- 标注特殊情况：`英文`、`付费墙`、`大陆可能无法访问`
- **只链接原始出处**，不链接公众号转载或聚合站

**③ 整期层面**

- 刊头写明收录截止时间：「收录截至 10/08 06:00」
- 页面底部写清楚：「AI 辅助整理 · 编辑人工审核 · 每条附原始来源」，再链接到编辑原则和更正记录
- 已更正的条目显示 `已更正` 标记，点开能看到改了什么

**④ 分享图上也带来源**

截图和海报会脱离网站传播，所以分享图上要印上**来源标签和来源名**（如「官方 · Anthropic 博客」）。这样被转发出去的内容依然可信，也能防止被别人删掉出处后当作谣言传播。

**⑤ 大陆读者打不开某些来源怎么办**

X、YouTube、部分 Google 页面和一些海外媒体在大陆打不开，微信里也常常拦截外链。对策：

- 有多个来源时，**把能访问的排在前面**（如官方博客、国内一线媒体的报道）
- 摘要里写清关键事实和原话，让读者不点链接也能核对
- 提供「复制链接」，方便读者换个环境打开

## 4. 产品结构与功能

### 4.1 页面结构

```
/                 今日（最新一期）
/d/2026-10-08     往期的某一期
/d/2026-10-08/3   单条新闻（分享落地页：打开整期并直接跳到第 3 条，带这条自己的分享信息）
/archive          往期列表
/about            关于 · 编辑原则 · 更正记录
/admin            后台：审核草稿、编辑、发布、连接 Agent（现有的聊天和设置页移到这里）
```

**不放底部导航栏。** 这是阅读型产品，导航越少越好。顶部只放刊头和"往期"入口。

### 4.2 功能清单

**P0：MVP（第 1–2 周）**

- 今日一期的阅读页：今日三件事（点一下跳到对应条目）、卡片原地展开 / 收起、阅读进度
- 左右滑动切换到上一期 / 下一期
- 读完页：读完的反馈、已连续阅读几期、「有用 / 一般」一键反馈、分享按钮、"明天 7:30 见"
- 分享：调用手机系统分享、复制链接、**生成分享图**（单条卡片 + 整期海报，都带二维码）
- 往期列表
- 深色模式（跟随系统设置）
- 可添加到手机主屏幕（PWA），**没网也能读今天这一期**
- 社交平台链接预览（X、Telegram、Slack 等能显示标题、摘要和封面）
- 后台：定时生成草稿 / 编辑 / 调整顺序 / 发布 / 撤回和更正
- 基础数据统计
- 页面底部标注"AI 辅助生成 · 人工审核"
- 资料包：发稿时存下每个来源的原文快照（读者看不到，为 AI 追问做准备）

**P1：第 3–6 周**

- 邮件订阅（每天 7:30 送到）
- 网页推送提醒（用户把网站添加到主屏幕之后）
- **一键导出小红书 / 朋友圈用的 3:4 卡片组**
- RSS 订阅
- 数据看板
- 周六的"一周回顾"
- **AI 追问第一步：预设追问**（见第 6 节）
- AI 追问第二步：自由追问（视第一步数据决定，P1.5）

**P2：第 2–3 个月，根据数据决定做不做**

- 关注话题 / 公司：只把关注的内容**高亮**，不过滤掉其他内容，保证所有人看到的是同一期
- 事件时间线（例如把一次大模型发布的前后经过串起来）
- AI 名词词典
- 每周小测验（5 道题，帮助记忆，也方便分享）
- 账号体系，以及收藏的多设备同步
- AI 追问第三步：深入调研

### 4.3 MVP 刻意不做的

| 不做 | 原因 |
| --- | --- |
| 登录注册 | 多一步就会流失一批人。连续阅读记录和已读状态先存在用户本地浏览器里 |
| 评论区 | 需要管理，容易变成吵架现场，也分散"5 分钟读完"的注意力 |
| 无限刷新的信息流 | 和"有终点"的原则冲突，也是竞品的通病 |
| 算法推荐 | 早期没有足够数据，而"大家看到同一期"本身就是一种共同话题 |
| 原生 App | 网页 + 添加到主屏幕已经够用，App 的分发成本太高 |
| 广告 | 早期只积累信任 |
| 实时 AI 问答 | 编造风险、成本和合规都需要先准备好。先用预设追问验证需求（见第 6 节） |

## 5. 移动端体验

### 5.1 打开后的第一屏（30 秒就有收获）

```
┌──────────────────────────────
│ AI 五分钟                往期 ›
│
│ 10.08
│ 周三 · 第 128 期 · 约 5 分钟
```

## 6. AI 追问：针对单条新闻继续问

### 6.1 要不要做

**结论：做。但不做成聊天机器人。** 它是一个"只针对这条新闻、只根据有出处的资料回答"的追问工具，分三步上线，每走一步都先看数据再决定下一步。

**价值**

- D 类读者想问「这是什么意思？」：降低理解门槛
- A 类读者想问「和之前有什么不同？跟我有什么关系？」：补上背景
- B 类读者想问「竞争对手怎么样？」：需要更多资料
- 顺带拿到一份宝贵的数据：**读者到底还想知道什么**。这能反过来改进写作。比如很多人点「这是什么」，说明摘要里的术语解释不够。

**必须正面解决的四个风险**

1. **编造**：一次瞎编就能毁掉"可信"这块招牌。这是最大的风险。
2. **偏离"有终点"**：一不小心就变成另一个聊天 App。
3. **成本和滥用**：每次提问都是一次计费的 Agent 调用，而网站是公开的，谁都能刷。
4. **合规**：面向大陆公众实时提供 AI 问答，要求比发布经过审核的内容高得多（见 6.8）。

### 6.2 分三步走

| 阶段 | 形态 | 回答从哪来 | 实时调用 AI | 人工审核 | 进入条件 |
| --- | --- | --- | --- | --- | --- |
| **第一步：预设追问**（P1） | 每条新闻下面 2–3 个问题按钮 | 发稿时和草稿一起生成 | 否 | 是，并入每日审核 | MVP 上线后即可做 |
| **第二步：自由追问**（P1.5） | 一个输入框，只能问这条新闻 | 只用这条新闻的**资料包** | 是 | 否，靠程序校验 + 每周抽检 | 预设追问使用率 ≥15%，且报错率 <1% |
| **第三步：深入调研**（P2） | 资料包答不了时，由用户主动点 | 联网检索新资料 | 是（较慢） | 否，明确标"未经编辑审核" | 自由追问里"资料没提到"的比例较高 |

**为什么从预设追问开始**：没有实时成本，审核过就不会有编造，在合规上和新闻正文一样属于"发布的内容"，还能先验证用户是不是真的想追问。

预设问题要**针对这条新闻定制**，不用千篇一律的模板。例如融资新闻问「钱打算花在哪？」，模型发布问「普通人现在能用上吗？」。

### 6.3 资料包：AI 只能看这些

每条新闻在发稿时就建好资料包。**从 MVP 起就开始存**：成本很低，以后做追问时就有现成的资料。

| 内容 | 说明 |
| --- | --- |
| 原文快照 | 每个来源的正文，记录抓取时间 |
| 这条新闻本身 | 标题、摘要、为什么重要、要点 |
| 本站的历史条目 | 同一家公司 / 同一话题过往的条目。**存档越久越值钱，是别人抄不走的积累** |
| 编辑备注（可选） | 编辑补充的背景 |

- 付费墙来源只能拿到标题和公开摘要，要标"仅部分内容"
- 快照只给 AI 读取和校验用，**不向读者展示全文**（版权原因）

### 6.4 "实事求是"的六道防线

关键思路：**不靠 AI 自觉，靠程序验证。**

**① 只给资料**

提示词里只放资料包，并写明：资料以外的知识不能当作事实陈述。

**② 先判断能不能答，再作答**

| 判断 | 怎么回答 |
| --- | --- |
| ✓ 资料中有明确答案 | 正常回答 |
| ◐ 资料只提到一部分 | 只回答有依据的部分，明确说哪部分没有提到 |
| ✕ 资料中没有 | 直接说"本条来源中没有提到"，**不猜**；提供「深入调研」按钮 |
| ⊘ 超出范围 | 与这条新闻无关、投资 / 医疗 / 法律建议、预测涨跌、敏感话题：礼貌拒绝 |

**③ 每句事实都要带引用和原文摘句**

AI 必须输出结构化结果：每一句事实都标明出自哪个来源，并附上一小段原文摘句（逐字摘抄）。

**④ 程序校验引用（最关键的一道）**

Worker 逐句检查两件事：引用的来源是否真的在资料包里？摘句是否真的出现在原文快照里？（规范化空格和标点后做字符串匹配）

- 不通过的句子直接删掉
- 剩下的内容不够回答问题，就降级为"✕ 资料中没有"

这样，"相信 AI"就变成了"验证 AI"。

**⑤ 事实和分析分开**

允许少量分析（如"这意味着……"），但必须标"分析"，而且只能建立在已经引用过的事实上。不做预测。

**⑥ 写明时间边界**

每个回答都注明"依据截至 10/08 06:00 的资料"。用户问到发布之后的进展，引导去深入调研。

**另外**：用户的问题和网页原文都只当作"资料"处理，不当作指令，以防有人在问题或网页里藏指令（提示词注入）。就算 AI 被带偏，第④道校验也会拦住没有依据的内容。

### 6.5 深入调研怎么做才不乱来

- **用户主动点才触发**，从不自动调研
- **优先检索白名单信源**：先查 3.7 清单里的 T1 / T2 来源，T3 只能当线索
- **同样做引用校验**：新找到的来源也要抓取原文，摘句必须对得上
- **结果明确标注**：「深入调研 · 未经编辑审核 · 生成于 10/09 08:12」。每个新来源同样显示 `官方` / `媒体` / `传闻` 标签
- **找不到就如实说**：「没有找到可靠来源」也是一个合格的回答
- **结果缓存、所有人共享**：同一条新闻的同一个问题，后来的人直接看已有结果
- **形成正向循环**：被问得多的调研问题进入编辑队列，审核后升级成预设追问
- **异步进行**：大约需要 30 秒到 2 分钟。用户可以先关掉面板继续读，好了在卡片上提示

**Agent 分工**：建议在 Manyfold 上准备两个独立的 Agent。

- **追问 Agent**：不联网，只读资料包
- **调研 Agent**：可以联网检索

职责分开，约束和计费都更清楚。注意，"不联网"只能靠提示词要求 Agent 做到，真正的硬保证来自 6.4 的程序校验。

### 6.6 交互设计

```

│ 想多了解一点？
│ [普通人现在能用上吗？] [和上一代比有什么不同？]
│ [问点别的…]

点击后，从底部弹出半屏面板：
┌──────────────────────────────
│ 追问 · 某实验室开源 70B 模型          ✕
│
│ 和上一代比有什么不同？
│ ✓ 来源中有明确答案
│ 参数量从 32B 增加到 70B [1]，官方称代码
│ 评测得分提升 18% [1]。媒体报道称推理成本
│ 约为同级闭源模型的 1/8 [2]。
│
│ [1] 官方 · ××博客  "…原文摘句…"
│ [2] 媒体 · 36氪    "…原文摘句…"
│
│ 依据截至 10/08 06:00 的资料 · AI 生成
│ 👍  👎  报错
│ ──────────────
│ [继续问这条…]               还可问 2 次
└──────────────────────────────

资料中没有答案时：
│ 和 GPT-5 比谁更强？
│ ✕ 本条来源中没有提到和 GPT-5 的直接对比。
│   [深入调研（约 1 分钟）]
```

**交互规则**

- 用半屏面板展示，下滑就能关闭，关闭后回到原来的阅读位置，**不打断主流程**
- 每个回答 ≤150 字，保持"短"的风格
- 引用编号 `[1]` 可以点，展开原文摘句和原文链接
- 每条新闻最多连续追问 3 次，不能跨新闻闲聊
- 追问不计入"5 分钟"，也不影响"读完"的判定
- 用户点"报错"后，这个回答进入编辑队列

### 6.7 成本与防滥用（第二、三步才需要）

| 措施 | 做法 |
| --- | --- |
| 个人额度 | 每人每天自由追问 10 次、深入调研 2 次（按匿名访客 ID 和 IP 同时计数） |
| 全站预算上限 | 每天的 Agent 调用设上限，超出后自动降级为只显示预设追问 |
| 人机验证 | 第一次提问前过 Cloudflare Turnstile |
| 问题长度 | ≤100 字 |
| 缓存 | 同一条新闻的同一个问题（规范化后完全相同），直接复用已通过校验的答案 |
| 防重复计费 | A2A 的 `messageId` 由提问记录的 ID 推导，重试不会重复计费（符合 AGENTS.md 的约定） |

> ⚠️ **需要改一条项目约定**：这是一个**公开的、会触发计费的接口**，正是 AGENTS.md 第 7 条的门禁要防的情况。要开例外，必须同时具备：人机验证 + 频率限制 + 全站预算上限 + 只能针对已发布的新闻提问。这些理由要一并写进 AGENTS.md。

### 6.8 合规（面向大陆用户时）

- **预设追问**：属于经过编辑审核后发布的内容，和新闻正文一样处理
- **自由追问 / 深入调研**：属于向公众实时提供生成式 AI 服务，适用《生成式人工智能服务管理暂行办法》，**可能需要完成相应的备案 / 登记和安全评估**。回答要按《人工智能生成合成内容标识办法》标注为 AI 生成
- **建议**：如果主要面向大陆用户，第二、三步上线前先做合规咨询。第一步不受影响
- **拒答范围**：政治敏感话题、投资建议、医疗和法律建议

### 6.9 怎么衡量

| 指标 | 目标 | 用来判断什么 |
| --- | --- | --- |
| 追问使用率 | 第一步 ≥15% 才进入第二步 | 需求是不是真的 |
| 各预设问题的点击分布 | 观察 | 改进写作：「这是什么」点得多，说明摘要解释不够 |
| 回答分布（✓ / ◐ / ✕） | ✕ 太多说明资料包太薄 | 指导抓取哪些资料 |
| 校验拦截率 | 看趋势 | 最直接反映 AI 编造倾向的指标 |
| 报错率 | < 1% | 读者眼中的准确度 |
| 每周抽检准确率 | ≥ 95% | 编辑每周抽 20 个回答，对照原文检查 |
| 完读率 | 不下降 | 确认追问没有把读者带离主流程 |
| 每千读者的 AI 成本 | 设上限 | 成本可控 |

### 7.1 留存：培养每天来看的习惯

## 8. 衡量指标

**北极星指标：每周至少读完 3 期的用户数**，也就是真正养成习惯的用户有多少。

| 指标 | 目标 | 说明 |
| --- | --- | --- |
| 完读率 | ≥ 60% | 最能说明产品是否健康 |
| 平均阅读时长 | 3–6 分钟 | 太短说明内容不吸引人，太长说明写得太啰嗦 |
| 次日回访 / 7 日 / 30 日留存 | 持续上升 | 看习惯有没有养成 |
| 有用率 | ≥ 80% | 读完页点 👍 的占比，直接反映内容质量 |
| 分享率 | ≥ 3% | 分享次数 ÷ 阅读人数，看传播力 |
| 原文点击率 | 观察 | 看读者对哪些话题有深入兴趣 |
| 卡片展开率 | 观察 | 反过来指导选题 |
| 订阅转化率（P1） | 观察 | 有多少读者愿意被提醒 |

AI 追问的专项指标见 6.9。

**统计工具**：Cloudflare Web Analytics（不用 Cookie，免费），加上自己建一张事件表，记录打开、展开、读完、分享。

## 9. 技术方案（基于当前仓库）

当前仓库用的是 Cloudflare Workers + Hono + React 19 + D1 + Manyfold Agent（A2A 协议），和这个产品很匹配。

### 9.1 复用和改动

| 模块 | 做法 |
| --- | --- |
| 现有的聊天 / 设置页 | 移到 `/admin`，作为后台。连接 Agent 的流程原样保留 |
| 定时任务 | 在 `wrangler.jsonc` 加 `triggers.crons: ["30 21 * * *"]`（UTC 21:30 = 北京时间 05:30），Worker 增加 `scheduled()` 处理函数 |
| 生成草稿 | 抓取信源 → 调用 Agent 的 `message/send` → 结构化 JSON 存为草稿。**`messageId` 由这一期的日期推导出来**，重试时不会重复计费（遵守 AGENTS.md 的约定） |
| 公开的只读接口 | `GET /api/issues/latest`、`GET /api/issues/:date`、`GET /api/issues`（往期列表） |
| 后台接口 | `/api/admin/*`，走现有的密码门禁 |
| 链接预览信息 | `/`、`/d/*` 由 Worker 用 HTMLRewriter 往页面里注入 OG 信息；需要把 `run_worker_first` 扩展到这些路径 |
| 前端 | 读者端和后台按路由分开打包，读者端保持极轻 |
| 分享图 | MVP 阶段在浏览器里用 Canvas 生成，没有服务端成本 |
| PWA | 添加 manifest 和 Service Worker，缓存最新一期 |
| 资料包 | 发稿流程里抓取原文、提取正文，存进 D1（体积大时改用 R2） |
| AI 追问 | `GET /api/items/:id/qa`（预设追问，公开只读）；`POST /api/items/:id/ask`（自由追问，公开接口，需要 6.7 里的全部防护）；引用校验在 Worker 里做，不交给 Agent |

> ⚠️ **需要改一条项目约定**：AGENTS.md 第 7 条规定，`/api/` 下除了 health 和 state 以外都必须过密码门禁。新闻站的读者接口必须公开，所以要给 `GET /api/issues*` 开白名单。理由：**只读、不调用 Agent、不涉及凭据、可以在边缘缓存**。同时更新 AGENTS.md。

## 11. 风险与对策

| 风险 | 对策 |
| --- | --- |
| AI 写错、编造内容 | 每条必须附一手来源链接；人工审核；公开更正记录 |
| AI 追问时编造 | 只按资料包回答，程序逐句校验引用，资料没有就说没有；分三步上线（见 6.4） |
| 版权 | 只写原创摘要并附原文链接；不转载全文、不盗图（MVP 不使用新闻配图） |
| 断更（运营太累） | 自动生成草稿，把每天的人工压到 15 分钟以内；周日休刊 |
| **中国大陆访问速度** | `workers.dev` 域名在大陆访问不稳定，**必须绑定自己的域名**，上线前在各地 4G 实测打开速度。如果主要面向大陆用户，长期要考虑备案 + 国内 CDN，或者把公众号作为主阵地 |
| 合规 | 按《人工智能生成合成内容标识办法》在页面标注"AI 辅助生成"；定位为行业技术资讯；规模做大之前，先咨询资讯类业务需要哪些资质 |
| 和别人长得一样 | 差异化放在"有终点 + 说人话 + 可信"，不拼条数和速度 |
